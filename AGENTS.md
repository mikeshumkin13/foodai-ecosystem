# Правила Codex для FoodAI Ecosystem

Эти правила обязательны для каждого следующего Codex-сеанса в этом репозитории.

## Первые действия

1. Сначала прочитать документацию:
   - `docs/PROJECT_CONTEXT.md`
   - `docs/ARCHITECTURE.md`
   - `docs/ROADMAP.md`
   - `docs/STATUS.md`
   - `docs/DECISIONS.md`
   - `docs/SECURITY.md`
   - `docs/API.md`
2. Проверить `git status` и текущую ветку.
3. Если реальный код противоречит документации, сначала определить причину.
4. Не ломать существующие API без явного решения в `docs/DECISIONS.md`.
5. Перед изменением архитектуры читать `docs/DECISIONS.md` и обновлять его новым решением.
6. После каждой задачи обновлять `docs/STATUS.md`.
7. Запускать доступные тесты и линтеры перед завершением задачи.
8. Не выполнять merge в `develop`, `main`, `release/*` или `hotfix/*` самостоятельно.

## Языки проекта

Основные языки проекта и пользовательского продукта: русский (`ru`) и английский (`en`).

По возможности вести проектную коммуникацию, статусы, PR-тексты и объяснения на русском. Если английский нужен для кода, команд, API, сторонних терминов или устойчивых технических формулировок, оставить английский термин или дублировать перевод.

Пользовательские тексты, публичные материалы, уведомления, safety-тексты, consent-тексты и UX-копирайтинг должны проектироваться с поддержкой русского и английского языков. Не хардкодить пользовательские строки так, чтобы это блокировало локализацию.

## GitFlow

- `main` — только стабильные релизы.
- `develop` — основная ветка разработки.
- Каждая логическая задача после создания `develop` выполняется в отдельной ветке `feature/*`.
- `release/*` используется для подготовки релизов.
- `hotfix/*` используется для критических production-исправлений.
- Никогда не разрабатывать напрямую в `main`.
- Никогда не выполнять merge самостоятельно без явной команды пользователя.

## Архитектура

- Стартуем с monorepo.
- `backend` — модульный Django-монолит.
- `services/vision` — отдельный FastAPI-сервис только из-за других CV/ML-зависимостей и требований к ресурсам.
- Не создавать микросервисы без конкретной необходимости.

## Product Safety

FoodAI Ecosystem не является врачом, лицензированным нутрициологом, психологом или системой медицинских решений.

AI не должен:

- ставить диагнозы;
- назначать лекарства;
- заменять врача;
- самостоятельно принимать медицинские решения.

Потенциально опасные ситуации требуют отдельной safety-логики.

## Security-by-design

- Least privilege.
- Deny by default.
- Минимизация собираемых данных.
- Секреты только через environment variables.
- `.env` никогда не коммитить.
- Фото пользователей приватны по умолчанию.
- Нужны object-level permissions и защита от IDOR.
- Логи не должны содержать пароли, токены, health profile, фотографии и другую чувствительную информацию.
